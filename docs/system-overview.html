01これは結局、何のシステムなのか

一言でいうと 「Electron デスクトップアプリ＋Node サーバー（server.js）が、複数の Claude エージェントを階層構造で動かすオーケストレーター」 です。Yuta の指示は必ず統括秘書ジェニーが受け、配下に委託します。

階層モデル（agents.json / company-registry.js）

Yuta（あなた） │ 指示はすべてここへ ▼ L0 ジェニー（統括秘書） … 分類・委託・報告集約 ▼ DELEGATE / SPAWN_TEAMMATE L1 事業部長 / PdM補佐 ティアラ・ハル・リオ ほか ▼ L2 PM補佐 トム(Overdue.)・ナギ・コウ・ユキ ほか ▼ L3 専門担当 レン(調査)・ノーラ(法務)・フィン(財務)・ソフィア(デザイン) ほか

agents.json には計30体が定義され、各々ロール・担当プロジェクト・階層レベルを持つ。階層は getAgentHierarchyLevel()（company-registry.js:302）がロール名から自動判定。

2つの実行モード（ここが要注意）

同じ「委託」でも、内部ではまったく別物の2系統が走ります。これが本システムを理解する最重要ポイントです。

① AgentTeamsManager 移行途上

spawn('claude', …) で本物の Claude Code CLI を別プロセスで起動。CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1。ジェニーが SPAWN_TEAMMATE を出すと配下を子プロセスとして立ち上げ、stdin/stdout の JSON ストリームで連携。

→ これが実現すれば「30個のターミナル Claude Code を秘書が統率する」に近い。ただし実体ファイル .claude/agents/*.md は8体分しかない(jenny/jesse/kai/len/luca/ren/tiara/tom)。残り22体はこのモードで起動できない。

② AgentExecutor フォールバック

ジェニーが居ないとき用。Anthropic API を直接 fetch し、###DELEGATE### ブロックを正規表現で拾って同一プロセス内で execute() を再帰呼び出し（agent-executor.js:181）。深さ6で停止。

→ 各段は単発の LLM 補完にすぎず、ツールはほぼ web_search のみ。実態は「プロンプト上のロールプレイ」に近く、ファイル操作や本格的なエージェントループは持たない。

CLAUDE.md が重要ファイルとして挙げる lib/claude-code-executor.js / lib/task-list.js / lib/agent-mailbox.js はいずれも実在しません。タスク状態は tasks.json への同期書き込み、エージェント間通知は WebSocket ブロードキャストで代替。＝ドキュメントと実装が乖離しており、設計が途中で組み替わった痕跡です。

02「指示なしで勝手に進む」はどこまで本当か

能動性の種類実装中身
毎朝9時ブリーフィングありscheduleDaily()。昨日のログ+ルーティンを集めジェニーが自動で要約発火
1時間ごとの見回りありrunAutonomousCheck()。停滞エージェント/タスク/プロジェクトを検知し再確認を投げる
停滞検知（48hルール）あり更新が48h止まったタスクを担当へ自動リマインド

gitコミット検知→次提案なしgit連携は30分ごとの自動push(git-autosync.js)のみ。コミットをトリガーにした能動行動は無し

厳しい現実：「能動性」の正体は “定時の見回りと小突き” です。

実装されている自走は 「止まっているものを見つけて『どうなってる?』と聞く」 レベル。「このプロジェクトを完成させるために、次は◯◯が必要だから自分で着手する」という目標駆動の計画→実行ループは存在しません。 停滞を検知しても、やることは“担当への確認メッセージ生成”であって、担当が実際に手を動かして成果物を出し切る保証はない。つまり 進捗を監視する仕組みはあるが、進捗を生む仕組みが弱い。

03ターミナルで複数の Claude Code を回すのと何が違うのか

これは一番大事な問いです。正直に答えると——「弱いモード(②API直叩き)で動いている限り、ターミナルの素の Claude Code の方が有能」です。理由を整理します。

OneCompanyOps が “足している” もの

  • 永続状態：tasks.json / workspace-memory にプロジェクト記憶が残る（ターミナルは閉じれば消える）
  • 定時自走：朝9時・毎時の自動起動（人間が叩かなくても動く）
  • 役割と階層：30体のロール定義・担当割り当て・報告ルート
  • UI と通知：進捗の可視化、WebSocket ブロードキャスト
  • マルチプロバイダ：軽い処理を Gemini に逃がしてコスト削減
  • GitHub連携：リポジトリ読取・PR作成（要token）

素のターミナル Claude Code の方が強い点

  • 本物のエージェントループ：ファイル編集・bash・検索・MCPを自律的に何十手も回す
  • フルツールアクセス：②API直叩きモードは web_search 程度しか持たない
  • MCP が全部使える：Notion/Drive/Gmail等（後述、本システムのエージェントからは呼べない）
  • 柔軟性：固定階層に縛られず、状況に応じて自分で手段を選ぶ
  • 枯れている：自作オーケストレーション特有のバグが無い

差別化の本命は①(AgentTeamsManager)＝「本物の Claude Code を秘書が束ねる」モードにしかない。

①が全エージェント分そろえば、「Yutaが秘書に一言 → 秘書が適切な部署の Claude Code プロセスを起動 → 各自がフルツールで実作業 → 秘書に報告集約」という、ターミナルを30枚開いて手動で振り分ける作業を自動化した状態になります。これこそが「ターミナルとの違い」の答え。
ところが現状、実体ファイルは8体分のみ。残りはagents.jsonに名前があるだけで①では起動せず②に落ちる。＝差別化の心臓部が3割しか組み上がっていない。

04柔軟性 — gitを読む・ネット検索・最適解を探す力

能力状態実態
Gitリポジトリ/コード読取使えるgithub-connector.js + workspace-manager.js で clone・読取・PR。ただし repoPath と token 設定済みプロジェクトのみ
Web検索条件付きAnthropic web_search_20250305。ロール名に「リサーチ/調査/analyst」を含むエージェントだけ付与。全員は使えない
MCP連携(Notion/Sheets/Calendar)設定のみコネクタは実装済みだが UI/手動API経由でしか動かず、エージェントが自分の判断で呼ぶ導線がない
MCP連携(Gmail/Drive)未実装package.json に名前があるだけ。実装ファイルなし
タスク重さの自動判定使えるtask-classifier.js が instant/light/heavy/complex を判定→モデル自動選択
「自分で手段を選び最適解を探す」弱い②モードは固定階層＆事前割当ツールのみ。“このタスクには検索が要る”と自己判断してツールを選ぶ裁量がない。①モードなら素のClaude Code並に柔軟だが、前述の8体制約

つまり柔軟性は 「①モードのエージェント＝高い / ②モードのエージェント＝低い」 と二極化しています。「git読んで・ネット調べて・最適解を探す」は、①で起動できる8体なら可能、②に落ちる22体ではほぼ不可、というのが正確な姿です。

05コスト構造 — どこで課金が膨らむか

モデルルーティング（llm-router.js）

タスク種別使用モデル狙い
classify / title / instant（挨拶・分類）Gemini 2.0 Flash激安・高速で雑処理を捌く
briefing / light（軽い調査）Gemini 1.5 Pro（無ければHaiku）中量級を安く
heavy / complex / secretary / agentClaude Sonnet 4委託・実作業はSonnet固定

設計思想は良い：軽い処理を Gemini に逃がして Anthropic 課金を節約している。ただし Gemini/OpenAI キーは app-settings.json の手動編集が必要でUI未整備。

コストが膨らむ構造

Yuta「タスクXやって」 ├ Gemini 分類(classify) … 安 ├ Gemini 曖昧性チェック … 安 ├ Sonnet ジェニー: 部長を特定・委託 │ └ Sonnet 部長: PM/担当へ再委託 │ └ Sonnet PM: 担当へ分配 │ └ Sonnet 担当: 実行 └ + 各段の報告(DIVISION_REPORT / COMPLETED)解析 → 単純な1タスクでも Sonnet が最低3〜4回発火

最大の欠陥：トークン/コスト追跡が完全に未実装。

API レスポンスに usage:{input_tokens,output_tokens} が返っているのに 一切記録していない（anthropic-stream.js）。月いくら使ったか、どのエージェントが高いか、暴走で課金が爆発していないか——誰にも見えない。「ガンガン進める」を本気でやるなら、自走ループ×階層委託×Sonnet多発で課金は容易に膨らむ。可視化と上限設定なしに自走を強めるのは危険です。これも「使うのが怖い/止めた」要因になり得ます。

06理想状態とのギャップ

理想：「有能な秘書の下に会社のような各部署があり、すべて勝手に進み、大事なことだけ承認・意思決定を聞きに来る」

理想
秘書が会社全体の状態を把握し、各部署が目標から逆算して自分で計画→実行→完成まで持っていく
現状 差大
秘書は来た指示を振り分けるのが主。各部署は振られた単発タスクを1回処理するだけで、完成まで自走する計画ループがない
理想
進捗が止まったら自分で原因を解消して前に進める
現状 差中
停滞は検知できるが、やるのは「確認メッセージ」止まり。解消は人/次の指示頼み
理想
大事なことだけ承認・意思決定を求めてくる（重要度のフィルタリング）
現状 仕組みなし
承認待ち/意思決定待ちを構造化する導線が存在しない。通知ブロードキャストはあるが「これはYutaの判断が必要」を選り分けてキューに積む機構がない
理想
30の部署すべてがフルの実行能力で動く
現状 8/30
本物プロセスで動けるのは8体。残りは弱い②モードに落ち、実作業能力が低い
理想
成果物の品質を担保して報告（信頼できる）
現状 弱い
QA担当(クイン)は定義上いるが、成果物を検証してから完了にする品質ループが組み込まれていない。完了報告＝自己申告

07どう改善すべきか（優先度順）

「理想」に寄せるための最短ルート。上から効きます。

1

実行モードを①(AgentTeamsManager)に一本化し、30体分の .claude/agents/*.md を揃える ［効果：特大 / 労力：中］

これが差別化の心臓。②API直叩きは「弱いロールプレイ」なので、本物のClaude Codeプロセスで全員動かす。agents.jsonの定義から .md を自動生成するスクリプトを書けば一気に埋まる。これだけで「ターミナル30枚を秘書が束ねる」状態に到達する。

2

コスト可視化＋月次上限ガードを実装 ［効果：大 / 労力：小］

anthropic-stream.js で usage を拾って activity-logger に記録するだけ。エージェント別・日次のトークン/概算円を出し、上限超過で自走を自動停止。これが無いと安心して自走を強められない。最小労力で最大の安心。

3

「承認・意思決定キュー」を新設 ［効果：大 / 労力：中］

理想の核心「大事なことだけ聞きに来る」。エージェントが ###NEEDS_DECISION### を出せる仕組みを作り、選択肢付きでYuta専用の承認インボックスに積む。Yutaは溜まった意思決定だけ捌けばよくなる。通知の垂れ流しを“承認待ち”に構造化する。

4

“見回り”を“前進”に格上げ — 目標駆動の計画ループ ［効果：特大 / 労力：大］

停滞検知時に「確認メッセージ」を出すのではなく、担当エージェントが「ゴール状態 vs 現状」を比較し、次の具体タスクを自分で生成して着手するループに。projects.md にゴール/完了条件を持たせ、毎時の自走でそこへ近づける差分を実行させる。これで初めて「勝手に進む」になる。

5

完了前の品質ゲート（QAクインを実装フローに組み込む） ［効果：中 / 労力：中］

担当が「完了」を出す前に、QA/レビュー担当が成果物を検証して合格して初めて review→done。自己申告完了をなくし、報告の信頼性を上げる。

6

MCP（Notion/Calendar/Sheets/Drive/Gmail）をエージェントツールとして開放 ［効果：中 / 労力：中］

①モードに寄せれば Claude Code 標準のMCP接続がそのまま使えるため、1とセットで進めると効率的。エージェントが自分でカレンダー確認・Notion更新・メール下書きまでできるようになる。

補足：本レポートはコード静的解析に基づく。CLAUDE.md と実装の乖離（実在しないファイルの記載、30体定義 vs 8体実体）が複数確認されたため、まず 「設計ドキュメントと実装の現状を一致させる棚卸し」 を最初の一歩にすると、以降の改善判断がぶれません。
